Things I built, and why.

Platform and developer-experience work: tooling that removes friction, automation that is safe to re-run, and AI systems with a gate in front of every risky step.

This work is internal to the studios I have worked at, so I describe the problem, the design decisions and the outcome rather than proprietary detail. Happy to go deeper in conversation.

Unblocking a 56,000-Workspace Version Control Migration

EA
Python · version control · AI-assisted refactor · migration support

The project's version control workspaces had to be migrated. A workspace is one person's checked-out view of the project in source control — every developer, artist and build machine holds at least one, which is why a single project runs to 56,000+ of them. Every migration pass needed a current list of which workspaces still had to move, and the script that fetched that list took multiple hours per run. So the list was stale before anyone could act on it, and each hand-off between teams cost most of a day in waiting.

  • Treated the slow query as the migration blocker it actually was, not as a reporting annoyance. The migration could only move as fast as the list refreshed.
  • Refactored the fetch with AI assistance, then verified by measurement. Generated code was read, run, and timed against the real estate before it was trusted — the speed-up is a measured number, not an assumption.
  • Moved the expensive work out of the per-record path so it happens once per run instead of 56,000 times.
  • Kept per-record failures isolated so one bad workspace cannot abort a whole run and force a restart mid-migration.

Outcome: runtime fell from hours to seconds. An updated workspace list could be produced and handed back inside the same conversation, so the migration stopped waiting on its own data and the cutover ran smoothly. The tool then became the team's routine version control hygiene check — the first time workspace cleanup was cheap enough to do as a habit rather than a project.

A Self-Serve Support Platform, End to End

EA
Slack intake · retrieval grounding · injection defence · cost control · deflection metrics · low-code port

Engineers asked the same support questions week after week, and every repeat interrupted someone on the team. Requests arrived as free-form messages, so they were inconsistent, hard to prioritise and impossible to measure — nobody could prove which docs were actually helping. A naive chatbot would have been worse than nothing: a confident wrong answer in a support channel costs more than no answer at all. So I built the whole path, from how a request arrives to how it gets answered.

Stage one — the front door

  • Put self-serve docs in front of the ticket. The intake form offers the relevant documentation first and asks whether it resolved the issue. Only a "no" creates a ticket.
  • Auto-triage by urgency, with a deliberate cap: anything marked highest severity is filed one level lower and flagged for human review, so a self-declared emergency cannot page the team automatically.
  • Made deflection measurable. Resolved-by-docs outcomes are recorded too, not just escalations — otherwise the deflection rate has no denominator and the whole metric is meaningless.

Stage two — the answers

  • Mined 9 support channels for a specific signal: issues resolved by conversation alone, with no code change, no hotfix and no filed ticket. Those are precisely the questions a self-serve answer can absorb. The corpus grew from 46 to 76 entries, each tagged with the symptom, what actually resolved it, and a confidence level.
  • Found the retrieval bug that made the corpus useless. Matching was a plain substring test, so tag-derived keywords scored zero against anything a human types. I replaced them with the short phrases people really use, then measured it: 16 of 16 real phrasings returned the correct document as the top hit.
  • Made regeneration idempotent — re-running the pipeline produces byte-identical output, so a rebuild is never a risky change. Auto-reply is gated on confidence: high-confidence entries answer automatically, medium-confidence entries require human review first.

Stage three — the assistant

  • Grounded answers with a strict source order: curated answers → internal wiki → source code → historical chat. Every reply cites where it came from, and lower-trust sources can never outrank current documentation.
  • Deterministic first, model second. A rules pre-filter answers the most common questions with zero model calls. Retrieval needs no vector database either — it is keyword and file-path scoring, which costs nothing to run and is trivial to debug.
  • Built a tool-identity gate after a dry run caught a real misfire. A question about one tool was being answered from a different tool's config file, because the two shared generic wording. Now, if a request does not name a known tool, the bot escalates to a human instead of guessing.
  • Treated all user text as untrusted. Prompt-injection guards plus a source-link allowlist, so text written by someone else cannot widen the search scope or make the bot emit an unapproved link. A test proves an injected scope override is neutralised.
  • Cost controls as a first-class feature: a cheap model classifies and a strong model is reserved for genuine ambiguity; per-request token and cost telemetry; a daily spend cap with an automatic kill switch. A verified answer is cached and reused for zero tokens, and expires itself when the source file it was grounded on changes.
  • Staged rollout with a gate between stages: log-only shadow mode on real traffic → posting for high-confidence, known-tool cases only → wider coverage. A replayable fixture of real requests and a mock model mode let the whole pipeline be verified offline, so a missing credential can never block a demo.

Stage four — a lighter version other people can edit

  • Ported a smaller version onto a low-code workflow platform so someone who does not write Python can change the answer flow. I also said out loud what could not come with it: two tiers read a local source checkout, and a hosted platform cannot reach a local disk. This is a different, lighter tool, not a replacement — selling it as a replacement would have been the actual risk.
  • Generated the workflow file from code instead of hand-writing it. Three script nodes hold around 200 lines of logic, and hand-escaping that into JSON is the most reliable way to ship a file the platform then refuses to import. The generator is the source of truth; the exported workflow is a build artefact.
  • One question per run, oldest first — which removes the cross-node record pairing that is where these workflows usually break. The first run deliberately primes and stops, or the bot would answer the entire channel backlog on day one. A message is marked handled before the model call, so a crash mid-run cannot produce a double reply.
  • Debugged by reading the platform's own execution database, not by clicking through its UI. That is how three retrieval bugs surfaced, every one of them returning a successful empty result: the chat search needed a channel name where an ID matched nothing at all; sorting by recency quietly shrank the result set and hid the correct answer that relevance ranking found; and documentation hits were starving chat hits out of the evidence list, so fixing the first bug alone changed nothing. The same question went from escalating at 0.2 confidence to answering correctly at 0.75.
  • Refused to tune the confidence threshold on a single example. One question at temperature zero returned 0.6 on one run and 0.7 on the next, so the threshold was sitting on the noise rather than above it. I left it untouched and collected shadow runs across different questions to set it from data.

Outcome: 323 automated tests, a pipeline that can be replayed offline, and the safety property the rollout depends on — an unknown tool escalates rather than answers. Intake now captures priority, owning tool and outcome on every request, so deflection rate, escalation volume and tool hotspots come from data the workflow records itself. One tool's answer coverage went from 10 entries to 31. The low-code version runs end to end on real messages in shadow mode, posting nothing.

Measure Before You BuyBuild-vs-buy

EA
Cost modelling · demand measurement · platform research

The team was about to request a paid automation platform of its own — a fixed monthly fee per environment, plus a charge on every single run. The proposal read well. What nobody had done was measure how much traffic the thing would actually serve, and a per-run charge is only cheap if you know the number of runs.

  • Counted real demand before costing anything. I pulled the actual message history of the target channels instead of estimating from impressions. They were quiet — the busiest one carried a few dozen messages a month, which reduced to roughly a dozen genuine questions.
  • Found the fixed cost was the whole bill. At real volume the monthly rent worked out to about 98% of the total, so owning a pair of environments cost roughly 50x more per question than being a tenant on an instance that already existed. The intuition that heavy usage justifies ownership is exactly backwards for a quiet support channel.
  • Priced the trigger shape, because that is what the charge is levied on. A short polling interval bills on every tick whether or not anyone asked a question, which made it the most expensive option by an order of magnitude. An event-driven trigger costs nothing while a channel is idle — a one-node change that was worth more than every other optimisation combined.
  • Measured the model cost too, and it was the smaller number — around 8x less than the platform's own per-run fee. So tightening the prompt was pointless and reducing the number of runs was everything. Knowing which number to chase is most of the work.
  • Checked what already existed before buying. An instance owned by another team was already open to us, and the platform team's own dashboards gave real cost and execution figures rather than my projections. The purchase request was cancelled.
  • Did the noisy iteration locally in containers, where runs are free, pinned to the same platform version as the hosted instance — so experiments cost nothing and the finished workflow still imported cleanly. I also raised the overlap with our own CI work honestly, because it weakened my own earlier argument for buying.

Outcome: a purchase request withdrawn on measured evidence rather than on opinion, and the same capability delivered as a tenancy on existing infrastructure at a fraction of the cost per question. The measurement took under a day. The uncomfortable part is the useful part: the numbers argued against the plan I had brought in.

Self-Hosted CI PlatformProof of concept

EA
Jenkins · Configuration as Code · secrets from day one · deliberate scope

The team wanted to own its own CI instead of depending on an ageing shared system. The blocker was not technical — it was a maintenance-cost objection from leadership. Arguing was not going to move it. Scope was the other half of the problem: this covers our own team's products only, not the studio-wide build farm, and saying so early is what kept the proposal small enough to be credible.

  • Answered the objection with a working system instead of a document. Built a local sandbox that stands the whole controller up from an empty state.
  • Everything as code. Credentials and jobs are declared in a config file and never clicked into the UI, so the configuration is reviewable and reproducible.
  • Enterprise secrets service from day one, with zero credentials carried over from the old repository — and separate secret paths for staging and production.
  • Wrote the verification script first, so "it works" is a command anyone can run, not an opinion.
  • Designed the runner topology around a real constraint: Windows-only builds need agents that inherit a domain identity, which a Linux container cannot provide. The topology reflects that instead of fighting it.
  • Wrote down which system gets which job, on one capability rather than on preference. A build agent can be given a checkout of the source depot; a hosted workflow service cannot reach one. So scheduled work and anything that must read source goes here, and live chat listen-and-reply or anything a non-developer needs to edit goes to the workflow platform. This split cut against my own earlier argument for buying a second platform, which is the main reason I trust it.

Outcome: 16 of 16 checks pass from a wiped state. A working proof built with zero infrastructure ask — which was the direct answer to the maintenance-cost objection. It is still a proof of concept: the production instance depends on approvals I do not control, and the proposal says that plainly instead of assuming them.

Shared Integration Workstation Fleet

EA
Idempotent provisioning · evidence-led design · shared-machine security · remote administration

Technical directors ran a legacy integration script on whatever machine they happened to have. Setup drifted per machine, so results were inconsistent and failures were hard to reproduce.

  • Wrote an idempotent provisioning tool. Re-running it reports "already matches" and changes nothing. Safe to run any number of times.
  • Designed from live data, not assumptions. Read 43 real existing workspaces to learn the actual mapping convention before writing a line of the tool — which is how the naming rule and the shared-path requirement were discovered rather than guessed.
  • Deliberately left syncing out. The integration script already syncs when it runs; duplicating that would have made setup slow and fragile for no gain.
  • Shipped a drag-and-drop setup kit that installs to the all-users desktop, so every person on a shared box gets the same tools. It skips shortcuts whose target is missing rather than leaving dead links behind — and that branch has now fired on a real machine, where one tool genuinely was not present yet.
  • Administered the machines over remote management rather than a remote desktop session. Commands run non-interactively, so setup is scriptable and repeatable, and it sidesteps a clipboard defect in the desktop session that was quietly corrupting pasted commands. Read-only probe scripts run first, so I look before I touch.
  • Worked around a credential-delegation limit instead of weakening security to beat it. A remote session on the target machine cannot reach the software share — a second network hop with no delegated credential — but my own workstation can read the share and write to the target. So the installer routes through the workstation as a middle hop, then verifies the result back on the machine. It is dry run by default, mirrors rather than copies so a re-install leaves nothing stale behind, and needs an explicit flag to write anything.
  • Read the vendor package before trusting it, which turned out to matter. Its own helper script decides which product's executable to launch by reading the name of the folder it sits in, and the release shipped leftover scripts pointing at a sibling product's paths entirely. Installing to a sensible-looking path would have silently run the wrong application. The install pins the exact folder name and launches the binary directly.
  • Stopped the automation where honesty required it. One tool is a tray application whose first run is interactive, so the installer deliberately does not start it — a person launches it once and confirms the drive it maps. Claiming full automation there would have produced a machine that looked provisioned and was not.
  • Chose managed cloud secrets over a local plaintext file — on a machine many people share, a readable secret file also defeats rotation and leaves no audit trail. This cost more setup effort and was the right trade.
  • Documented the real blockers honestly, including one broken configuration that predated the work and belonged to another team, with an explanation of why the obvious quick fix would have silently routed files to the wrong place.

Outcome: 19 workspaces verified clean on the first machine, from a repeatable tool rather than manual setup. The shared toolset is installed and verified in place on that machine — file count and version checked by script rather than eyeballed — with one interactive first-run step left to a human by design. The second machine is next.

Documentation as a Reviewed Pipeline

EA
Docs as code · publish guards · technical writing

A critical administration runbook was edited by hand in the wiki. It drifted, changes could not be reviewed, and a bad edit went live with nothing to catch it.

  • Moved the page into source files. It is now generated and published from disk, never edited in the wiki UI, so a change gets reviewed like code.
  • Wrote a publisher that is dry-run by default. It only writes when explicitly told to, and it uses the standard library only, so it runs anywhere without a dependency install.
  • Added three publish-blocking guards: the document must be well-formed; every original figure must still be referenced; and no figure may point outside the known attachment list. All three were tested against deliberately corrupted input — a guard nobody has tried to break is not a guard.
  • Rewrote the page for two distinct audiences and split it accordingly, with 23 figures, so a first-time user and an administrator each have a path that fits them.
  • Simplified the routing advice so users have one obvious place to go, instead of three tools with unclear ownership.

Outcome: published live with 23 figures. A broken publish is now caught before it reaches readers rather than reported by them afterwards.

How I work

Deterministic before model

If a rule can answer it, a rule answers it. A model call is a cost and a risk, so it needs to earn its place.

Dry run by default

Anything that writes, posts or deploys starts in report-only mode. Writing is an explicit flag someone has to type.

Idempotent, so a re-run is boring

Running it twice does nothing the second time. That is what makes automation safe to hand to someone else.

A gate between every stage

Shadow, then narrow, then wide — never coupled. Plus a kill switch, because the useful question is how it stops.

Design from live data

Read what the system actually does before writing the tool. Most of the good decisions above came from that step.

Escalate instead of guessing

An honest "a human should look at this" beats a confident wrong answer, especially in a support channel.
