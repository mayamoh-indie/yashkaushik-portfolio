Triaging recurring support requests in Slack

EA

Improved documented answer coverage by 210% for one internal tool. The intake workflow also recorded whether documentation resolved a request or it needed escalation.

Engineers fielded repeated support questions, and free-form requests made it hard to prioritize issues or tell whether documentation helped.

When someone asked for help in Slack, the workflow offered documentation before opening a Jira ticket. Urgent requests went to a person. For common questions, the assistant used rules and cached answers. When it used Claude through AWS Bedrock, it cited internal sources and escalated uncertain answers.

I replayed past requests offline to check which documents the assistant retrieved and how it answered. I also added input safeguards, usage monitoring, and spend controls.

Status. In trial mode, I confirmed the low-code version could return useful answers. It was ready for production when my role at EA ended, before rollout.

Keeping a troubleshooting runbook accurate

EA

Published a reviewed runbook with separate instructions for users and administrators. Validation blocked malformed documents and unexpected or missing figure references before publication.

Status. The workflow was used to publish the runbook.

Version control audit optimization

EA

Cut a version control audit from hours to seconds, giving migration teams an updated list on demand.

Migration handoffs relied on a report that could take hours to generate. The outstanding workspaces could change before the report arrived.

I refactored the Python script to run expensive operations once per audit and isolate individual record failures. I reviewed the AI-assisted changes and measured the runtime on migration data.

Status. The result measures the audit runtime during the migration.

Automation platform cost analysis

EA

Identified an alternative with approximately 98% lower projected cost per request. The separate purchase request was withdrawn.

The proposed platform charged a recurring fee and a fee per execution. The team needed to know whether support demand justified a standalone instance.

I estimated request volume from support activity, modelled fixed fees, execution charges, and model costs, and compared a standalone instance with shared capacity. I also compared polling with event-driven triggers to account for idle executions.

Status. The percentage is a cost projection at observed demand. Actual savings were unmeasured.

How I work

Deterministic before model

If a rule can answer it, a rule answers it. A model call is a cost and a risk, so it needs to earn its place.

Dry run by default

Anything that writes, posts or deploys starts in report-only mode. Writing is an explicit flag someone has to type.

Safe to run again

A second run should leave matching configuration in place.

Review each rollout stage

Evaluate in shadow mode, then review the results before a limited rollout. Keep a way to stop the workflow.

Design from live data

Read what the system actually does before writing the tool. Most of the good decisions above came from that step.

Escalate instead of guessing

An honest "a human should look at this" beats a confident wrong answer, especially in a support channel.
